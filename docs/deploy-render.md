# Publish a ResourceOS test instance on Render

The root `render.yaml` Blueprint defines one Node web service, one managed PostgreSQL database and a persistent disk for evidence/journals. This is an authenticated demonstration with fictional records. The selected persistent service and database plans are paid; Render shows current pricing before creating resources. Review those prices in your account. There is no physical valve actuation.

## Create the services

1. Sign in to Render and connect the GitHub account that can access `Zizoummm/ressource-os`.
2. Use **New → Blueprint**, choose that repository, branch **main**, and the root `render.yaml`. Alternatively use the repository's Deploy to Render link in the README.
3. Review the web service, PostgreSQL database, persistent disk and current prices, then create the Blueprint.
4. Wait for the web service to become **Live**. The build installs dependencies, generates Prisma and compiles Next.js. Startup applies checksum-verified migrations, seeds a new demo database and listens on Render's `PORT`. The public `/api/health` returns 200 only when the database policy is present.
5. Open the service's actual HTTPS URL shown by Render. Its automatic `RENDER_EXTERNAL_URL` supplies the allowed origin, Secure cookie setting and PDF verification links. No localhost URL is used by the hosted instance.

No Render account credentials are included in the repository. A GitHub push or passing local tests does not establish that a Render deployment is live. The account owner must create the services in Render when no deployment credential is connected to the coding environment.

## Sign in

Use `operator@axiom.demo`, `regulator@axiom.demo`, `compliance@axiom.demo`, `inspector@axiom.demo`, `treasury@axiom.demo`, `auditor@axiom.demo` or `admin@axiom.demo`. The accounts use the private **DEMO_PASSWORD generated by Render** in the web service's Environment settings. It is different from the local `.env` password. Read it privately in Render; never commit it or paste it into chat. Use separate browser profiles for separate roles.

The Blueprint generates `DRT_SECRET` and `DEMO_PASSWORD`, binds `DATABASE_URL` to the internal database connection and keeps files under `RESOURCEOS_DATA_DIR=/var/data/resourceos`. PostgreSQL's external IP allowlist is empty. These values never need to be copied into source code.

The demo seed is enabled explicitly with `ALLOW_DEMO_SEED=true`. It preserves existing records on restart. Changing DEMO_PASSWORD later does **not** reset existing account hashes; keep the generated value stable or implement an explicit password-reset workflow. Keep DRT_SECRET stable to preserve verification of issued tokens.

## Test the instance

- Sign in as operator and open ARRS; the first demo cargo has a complete authorization path, the second is blocked, and the third has revoked evidence.
- Sign in as regulator in a separate browser profile and approve an eligible current cargo version. The operator issues the release token; the same officer cannot both approve and request the release.
- Open the QR verification page and download a PDF dossier. Withdraw a controlling POP/POF decision as compliance and confirm the prior token becomes REVOKED.
- Upload a small PDF as operator. Restart the web service from Render, sign in again and check that the document still downloads. It lives on the attached disk, not temporary build storage.
- ValveLab only operates on test cargos, consumes independent approval for OPEN and remains an in-process simulator. Registrations/positions reset on restart; journal files persist.

For a custom domain, configure the domain in Render and set `APP_URL` to that exact HTTPS origin. Leave APP_URL unset for the ordinary onrender.com address. The web service is a single instance because the simulator state is process-local and evidence uses a local persistent disk.

## Update and remove

Push reviewed changes to the connected branch and use Render's deploy controls (or its configured automatic deployment setting). PostgreSQL and evidence persist. Do not delete the disk or database to redeploy code. Back up both before schema changes. Local `.data/resourceos-snapshot.sql` files and local credentials are not uploaded; Render starts from fresh fictional seed data.

To end testing and stop recurring hosting charges, remove the test services, database and disk through Render after retaining any records you need. Infrastructure and data deletion are separate actions from deleting application code.

## Local validation of the hosted startup contract

With the local PostgreSQL service running:

```sh
npm run build
npm run test:hosted
```

The check creates its own temporary database and clean working directory without `.env`, injects Render-style HTTPS URL and PORT variables, tests authentication and Secure cookies, verifies protected evidence and tokens, restarts the service and verifies persistence. It deletes only its own temporary fixtures. This validates the application's hosting contract; only an actual Render deployment validates Render account, region, plan and provisioning availability.
