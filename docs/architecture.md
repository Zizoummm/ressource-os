# Architecture and trust boundaries

The application is a modular monolith. Browser → authenticated App Router handler → role/tenant policy → Zod-validated domain transaction → PostgreSQL. Only the public token verifier is anonymous. Producer users see their own organization's cargos, batches, documents and audit events. Institutional roles can review producers in the same tenant. The counterparty register is shared within that tenant. No principal can select a different tenant in a request.

Authorization has three separate layers: derived eligibility, independent human approval of an authorization version, then signed short-lived demonstration token issuance. Controlling mutations increment the version and revoke outstanding tokens in the same transaction. Financial policy changes invalidate affected authorizations and require assessments to match the new rates. Verification also checks current conditions so natural expiration cannot leave a token appearing valid.

Resource balances are reconstructed from batch production, append-only custody movements and allocations per location. Row locks plus serializable transactions reject simultaneous over-allocation. Audit writes commit together with successful mutations. Authenticated ARRS and ValveLab requests that fail are recorded after their transaction rolls back, without copying request bodies or credentials into the audit log. Ordinary application users have no audit update/delete API; database triggers additionally refuse these statements. Operational access to the database is a separate trust boundary.

Opaque session tokens are random, hashed before persistence and expire after eight hours. Passwords use bcrypt; disabling a user deletes sessions. Origin checking complements SameSite cookies. Data files are stored under random server-generated keys through `EvidenceStorage`; requests resolve an authorized database document before reading bytes. A future object-storage adapter can implement the same interface.

External registries, customs, banking, licensed inspectors, terminal operations, Treasury and the future Axiom Verify/PortOS/LogisticsOS/GovOS products are not implemented. They should write provenance-labelled evidence through reviewed adapters, with destination-scoped credentials and signed source references. `src/server/integrations.ts` defines the adapter boundary. No connector may directly assign a cargo RELEASED state or bypass the authorization transaction.

Experimental ValveLab remains a separate gateway interface. Its ResourceOS bridge derives eligibility from the same database engine and consumes approval for an OPEN attempt. Physical transport is intentionally absent. In-memory device registration/position and simulator replay state are not durable device infrastructure. Hardware integration requires a new reviewed implementation of the documented contract.
